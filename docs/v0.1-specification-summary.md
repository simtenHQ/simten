## Key Design Decisions

### 1. UI Widgets Are NOT Semantic Primitives

**WRONG:**
```
component sw1: SWITCH
component led1: LED
```

**RIGHT:**
```
input a: Bit
output sum: Bit
```

- SWITCH/LED are UI rendering choices, not circuit structure
- DSL describes structure, UI decides how to render inputs/outputs
- Inputs can be rendered as switches, buttons, or text fields
- Outputs can be rendered as LEDs, 7-segment displays, or text

### 2. Components Are NOT Keywords

**Critical for extensibility:**

```
DSL Text → AST (names only) → Symbol Resolution → IR Generation → Simulation
```

- At parse time: `node x1: Xor` just records a reference to "Xor"
- At link time: System resolves "Xor" to a component definition
- If missing: Link error, not parse error

**Built-ins (DSL keywords):**
- `circuit`, `input`, `output`, `clock`, `connect`, `node`, `state`
- Types: `Bit`, `Bus[N]`

**NOT built-ins (library components):**
- `And`, `Or`, `Xor`, `Not`, `Register`, `RAM`, `ALU`, etc.
- These are resolved by name at link time

### 3. Three Types of Components

| Type | Implementation | Expandable | Redefinable | Examples |
|------|---------------|------------|-------------|----------|
| **Primitive** | Simulator kernel (TypeScript) | No | No | And, Or, Register, RAM |
| **Composite** | DSL/IR (other components) | Yes | Yes (shadowing) | HalfAdder, FullAdder, ALU |
| **Intrinsic** | Special simulator logic | No | No | Display, Input, DebugProbe |

**Primitives** - Fast, optimized operations provided by simulator
**Composites** - User-extensible, built from other components
**Intrinsics** - UI/debugging components with side effects

### 4. Explicit Port Typing

Every port has:
- **Name**: `a`, `sum`, `data_in`
- **Type**: `Bit` or `Bus[N]`
- **Direction**: `input`, `output`, or `clock`

```
circuit FullAdder {
  input a: Bit
  input b: Bit
  input cin: Bit
  output sum: Bit
  output cout: Bit

  // ...
}
```

### 5. Clock and State Handling

**State declaration:**
```
state value: Bit = 0
state memory: Array[256, Bus[8]]
```

**Clock sensitivity:**
```
on clk rising {
  value = d  // Update on rising edge
}
```

**Combinational vs Sequential:**
- Combinational: No state, no clock (e.g., AND gate)
- Sequential: Has state, requires clock (e.g., Register)

### 6. Parameterization

Components can be parameterized:

```
circuit RippleCarryAdder(width: Int) {
  input a: Bus[width]
  input b: Bus[width]
  output sum: Bus[width]
  // ...
}

// Usage:
node adder: RippleCarryAdder(width = 8)
```

Parameters are compile-time constants, not runtime values.

### 7. JSON is IR, Not DSL

```
DSL (human-friendly) → Parser → AST → Linker → IR (JSON) → Simulator
                                                  ↓
                                           UI Projection
```

- DSL is source language for humans and LLMs
- IR is executable representation for simulator
- JSON is serialization format for IR
- UI reads IR and adds visual metadata

## Execution Model

### Combinational Circuits

1. Build dependency graph
2. Topological sort (detect cycles)
3. Evaluate nodes in dependency order
4. Propagate values to outputs

### Sequential Circuits

1. **Combinational phase**: Evaluate all combinational logic
2. **Clock edge detection**: Check for rising/falling edges
3. **State update phase**: Update registers/memory on clock edges
4. **Repeat next cycle**

### Simulation Loop

```typescript
class Simulator {
  step(inputs: Map<string, Value>): StepResult {
    // 1. Evaluate combinational logic
    const portValues = evaluateCombinational(this.circuit, inputs);

    // 2. Detect clock edges
    const edges = detectClockEdges(this.clockValues, this.prevClockValues);

    // 3. Update state on clock edges
    for (const stateBlock of this.circuit.state) {
      if (edges.get(stateBlock.clockRef) === stateBlock.edge) {
        this.state.set(stateBlock.id, computeNextState(stateBlock, portValues));
      }
    }

    // 4. Return results
    return { outputs: portValues, state: this.state };
  }
}
```

## LLM-Friendly Design

### Consistent Structure

Every circuit follows the same pattern:

```
circuit <Name> {
  // 1. Parameters (if any)
  // 2. Input ports
  // 3. Output ports
  // 4. Clock inputs
  // 5. State declarations
  // 6. Implementation
}
```

### Predictable Syntax

- Port references: `node.port` (always dot notation)
- Connections: `source -> target` (always left-to-right)
- Parameters: `Component(name = value)` (always named, never positional)

### Forgiving of Variations

- Whitespace-insensitive (within reason)
- Comments encouraged and ignored
- Declaration order flexible (inputs before outputs is convention, not requirement)

### Clear Error Messages

```
Error: Cannot resolve component 'HalfAder'

  Did you mean:
    - HalfAdder (std.arithmetic)
    - FullAdder (std.arithmetic)
```

### Self-Documenting

```
circuit FullAdder {
  // Adds three bits: a + b + carry_in
  // Produces sum and carry_out
  input a: Bit
  input b: Bit
  input cin: Bit
  output sum: Bit
  output cout: Bit

  impl {
    // First stage: add a and b
    node ha1: HalfAdder
    // ...
  }
}
```

## Type System

### Built-in Types

- `Bit` - Single binary value (true/false, 1/0)
- `Bus[N]` - N-bit wide bus (e.g., `Bus[8]` for 8 bits)
- `Word[N]` - Alias for `Bus[N]`

### Type Checking

- All connections must have matching types
- `Bit` connects to `Bit`
- `Bus[N]` connects to `Bus[N]` (same width)
- Explicit conversion required for mismatches

### Future Extensions

- `Array[N, T]` - Arrays of values
- `Struct { ... }` - Composite types
- `Enum { ... }` - Enumerated types

## Example: HalfAdder

### DSL
```
circuit HalfAdder {
  input a: Bit
  input b: Bit
  output sum: Bit
  output carry: Bit

  impl {
    node xor1: Xor
    node and1: And

    connect a -> xor1.a
    connect b -> xor1.b
    connect xor1.out -> sum

    connect a -> and1.a
    connect b -> and1.b
    connect and1.out -> carry
  }
}
```

### IR (simplified)
```json
{
  "name": "HalfAdder",
  "inputs": [
    { "name": "a", "portType": { "kind": "bit" } },
    { "name": "b", "portType": { "kind": "bit" } }
  ],
  "outputs": [
    { "name": "sum", "portType": { "kind": "bit" } },
    { "name": "carry", "portType": { "kind": "bit" } }
  ],
  "nodes": [
    { "id": "xor1", "componentRef": "Xor", ... },
    { "id": "and1", "componentRef": "And", ... }
  ],
  "connections": [
    { "source": { "nodeId": "", "portName": "a" },
      "target": { "nodeId": "xor1", "portName": "a" } },
    // ... more connections
  ]
}
```

### Execution
```
1. Topological sort: [] → [xor1, and1]
2. Evaluate xor1: inputs{a, b} → output{sum}
3. Evaluate and1: inputs{a, b} → output{carry}
4. Propagate to circuit outputs
```

## Validation Rules

1. **Type consistency** - All connections have matching types
2. **Single driver** - Each input has at most one source
3. **Acyclic combinational** - No combinational loops
4. **Valid references** - All component refs resolve
5. **Valid ports** - All port paths reference existing ports
6. **Clock consistency** - State blocks reference valid clocks

## Optimization Opportunities

1. **Constant propagation** - Replace constant expressions
2. **Dead code elimination** - Remove unused nodes
3. **Component inlining** - Flatten small composites
4. **Incremental evaluation** - Only re-evaluate changed nodes
5. **Bus width reduction** - Remove unused bits

## Future Extensions

1. **Import system** - `import std.arithmetic.Adder`
2. **Parameterized generation** - `for i in 0..N { ... }`
3. **Conditional compilation** - `if width > 8 { ... }`
4. **Assertions** - `assert sum == (a ^ b ^ cin)`
5. **Formal verification** - `property no_overflow { ... }`
6. **Multi-clock domains** - Multiple independent clocks

## Summary

The v0.1 specification provides:

✅ **Clear separation** - DSL (syntax) vs IR (semantics)
✅ **Extensibility** - Component library model, not hardcoded keywords
✅ **Type safety** - Explicit port types, connection validation
✅ **Deterministic execution** - Well-defined evaluation order
✅ **LLM-friendly** - Consistent, predictable syntax
✅ **Hierarchical composition** - Components built from components
✅ **Parameterization** - Generic, reusable components
✅ **State and clocking** - Sequential circuit support

The specification is locked down and ready for implementation.
