## Overview

Circuit code is arbitrary TypeScript. When you share a circuit or ask Claude to simulate one, that code executes on your machine. Simten runs it in two separate sandboxes — one for the browser, one for the MCP server — so untrusted code cannot access your credentials, your filesystem, or your app's state.

**Core invariant:** In: arbitrary TypeScript string. Out: plain JSON only. No functions, Maps, or class instances cross any boundary. Any dangerous code executes only inside the sandbox and its results are serialised to safe primitives before leaving.

## Browser Sandbox

When you type circuit code in the editor, it is compiled and simulated inside a hidden `<iframe>` served from a separate origin (`sandbox.simten.dev` in production, `localhost:3002` in development). The main app (`simten.dev` / `localhost:3001`) never executes user code directly.

### Two levels of isolation

**Origin isolation (iframe)**

The iframe is served from a different origin. The browser enforces a hard boundary: code inside `sandbox.simten.dev` cannot read `simten.dev` cookies, `localStorage`, auth tokens, or DOM. This is not a JavaScript check — it is enforced by the browser's same-origin policy at the OS level.

```html
<iframe
  src="https://sandbox.simten.dev"
  sandbox="allow-scripts allow-same-origin"
  style="display:none; width:0; height:0"
/>
```

`allow-same-origin` is required so the sandbox iframe can load its own scripts (Vite dev server, Cloudflare Pages). It does **not** weaken isolation: the escape hatch only applies when the iframe and parent share the same origin — they don't.

**Thread isolation (Web Worker)**

The iframe spawns a Web Worker for all user code execution (`executeCircuitCode`, `simulateCircuit`). Workers get their own OS thread. An infinite loop (`while(true){}`) blocks only the worker thread — the main app and the iframe event loop remain responsive.

```
localhost:3001 (main app)
└── localhost:3002 (hidden iframe — origin boundary)
    └── worker.ts (Web Worker — thread boundary)
        └── executeCircuitCode(userSource)  ← untrusted code runs here
```

### Timeout and recovery

The iframe sets a 5-second timeout per request. If the worker doesn't respond:
1. `worker.terminate()` kills the hung thread
2. A fresh worker is spawned immediately
3. Any requests queued while the worker was hung are resolved with `'Worker restarted'` so the caller can retry with the current (likely fixed) code

The main app never hangs. The iframe recovers transparently.

### What is and isn't blocked

| Attack | Status |
|--------|--------|
| Access `simten.dev` cookies / localStorage | Blocked — origin isolation |
| Access `simten.dev` DOM | Blocked — origin isolation |
| `window` object from user code | Blocked — runs in Worker (no `window`) |
| `localStorage` from user code | Blocked — `localStorage is not defined` in Worker |
| Infinite loop blocking the UI | Blocked — Worker on separate OS thread, 5s timeout |
| HTTP requests / crypto mining | Not blocked by origin isolation alone — no credentials reachable; CSP will be added with npm import support |

### postMessage boundary

All communication between the main app and the sandbox crosses a `postMessage` boundary. Only plain JSON is sent. The `compile` response returns `Circuit[]` (plain IR objects), not `BuiltCircuit` instances (which contain function references). The simulator is reconstructed from IR inside the iframe.

## MCP Sandbox

When Claude calls `simulate_circuit` or `check_circuit`, the circuit source runs in a forked child process — not in the MCP server process itself. The MCP process (which holds your `ANTHROPIC_API_KEY` and runs with your full filesystem access) never executes user circuit code.

### Architecture

```
MCP server process (full env, full fs)
└── fork() → sandbox-child.cjs (isolated child)
    ├── env: {}              — no API keys, no HOME, no PATH
    ├── --permission         — Node.js permission model
    ├── --allow-fs-read=<bundle-path>   — only the bundle itself
    └── executeCircuitCode(userSource)  ← untrusted code runs here
```

### Empty environment

The child is forked with `env: {}`. `process.env` is completely empty:

- `process.env.ANTHROPIC_API_KEY` → `undefined`
- `process.env.HOME` → `undefined`
- All other environment variables → `undefined`

Even if circuit code tries to read environment variables, there is nothing there to steal.

### Node.js Permission Model (`--permission`)

The child is started with Node.js's built-in permission model. With no `--allow-fs-read` paths specified (except the bundle itself), all filesystem reads throw `ERR_ACCESS_DENIED`:

```
fs.readFileSync('/etc/passwd')       → ERR_ACCESS_DENIED
fs.readFileSync('~/.ssh/id_rsa')     → ERR_ACCESS_DENIED
fs.readFileSync('~/.aws/credentials')→ ERR_ACCESS_DENIED
```

This is enforced at the Node.js runtime level — JavaScript overrides cannot bypass it.

With no `--allow-child-process`, subprocess spawning is also blocked:

```
child_process.exec('curl ...')  → ERR_ACCESS_DENIED
child_process.spawn('wget ...')  → ERR_ACCESS_DENIED
```

This blocks the `curl`-based exfiltration path (read a file, pipe it to an attacker's server) even if somehow the fs read succeeded.

### Self-contained bundle

The `--permission` model requires explicitly listing every file the child is allowed to read. Since the child needs to load `@simten/core` and its dependencies, naively listing all module paths would be fragile (especially with pnpm symlinks).

Instead, `sandbox-child.ts` is bundled at build time with esbuild into a single self-contained `sandbox-child.cjs` file. All dependencies are inlined — no external module reads are needed at runtime. The only `--allow-fs-read` needed is the path to the bundle itself.

```
pnpm build
# → tsc -b (compiles MCP TypeScript)
# → esbuild src/lib/sandbox-child.ts --bundle --platform=node --format=cjs
#         --outfile=dist/lib/sandbox-child.cjs
```

Note: Node.js 23.6 documents that the main script is "automatically allowed" under `--permission`, but the CJS loader uses `readFileSync` internally, which is subject to the permission check. An explicit `--allow-fs-read=<bundle-path>` is required.

### Lifecycle

- Spawned lazily on the first `simulate_circuit` or `check_circuit` call
- Reused across all subsequent calls in the same MCP session (~1–5ms IPC overhead, invisible in Claude's response latency)
- Killed and respawned on timeout (30s) or unexpected exit
- All requests pending against a dead child are resolved with an error immediately — no hanging

### What is and isn't blocked

| Attack | Status |
|--------|--------|
| `process.env.ANTHROPIC_API_KEY` | Blocked — `env: {}` |
| Read `~/.ssh/id_rsa` | Blocked — `--permission` |
| Read `~/.aws/credentials` | Blocked — `--permission` |
| Read any file outside the bundle | Blocked — `--permission` |
| `child_process.exec('curl ...')` | Blocked — `--permission`, no `--allow-child-process` |
| Infinite loop / hung simulation | Blocked — 30s timeout, kill + respawn |
| HTTP requests / crypto mining | Not blocked by `--permission` — but `env:{}` means no credentials to send; 30s timeout limits mining window |

## Known gaps

**Network access from both sandboxes** is not kernel-restricted. `http.request`, `net.Socket`, and `fetch` still work inside both the browser Worker and the MCP child process. This is acceptable because:

1. `env: {}` means the child has no credentials to exfiltrate
2. `--permission` means no files can be read to exfiltrate
3. The 30s (MCP) and 5s (browser) timeouts limit crypto mining windows
4. The browser worker runs on `localhost:3002` with no cookies, no tokens, no sensitive storage

Network restriction will be tightened when npm import support (`esm.sh`) is added — a `Content-Security-Policy: connect-src 'self' https://esm.sh` header on the sandbox server will whitelist only the CDN.
