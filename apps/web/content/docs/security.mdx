## Overview

Circuit code is arbitrary TypeScript. When you share a circuit or ask Claude to simulate one, that code executes on your machine. Simten runs it in two separate sandboxes — one for the browser, one for the MCP server — so untrusted code cannot access your credentials, your filesystem, or your app's state.

**Core invariant:** In: arbitrary TypeScript string. Out: plain JSON only. No functions, Maps, or class instances cross any boundary. Any dangerous code executes only inside the sandbox, and its results are serialised to safe primitives before leaving.

## Browser Sandbox

When you type circuit code in the editor, it compiles and simulates inside a hidden `<iframe>` served from a separate origin (`sandbox.simten.dev` in production, `localhost:3002` in development). The main app (`simten.dev` / `localhost:3001`) never executes user code directly — not even via `eval` or `new Function()`.

This applies to every code-execution surface: the editor, the live playground, and `<circuit-embed>` web components. All three route through the same sandbox.

### Two levels of isolation

**Origin isolation (iframe)**

The iframe is served from a different origin. The browser enforces a hard boundary: code inside `sandbox.simten.dev` cannot read `simten.dev` cookies, `localStorage`, auth tokens, or DOM. This is enforced by the browser's same-origin policy at the OS level — not a JavaScript check.

```html
<iframe
  src="https://sandbox.simten.dev"
  sandbox="allow-scripts allow-same-origin"
  style="display:none; width:0; height:0"
/>
```

`allow-same-origin` is required so the sandbox iframe can load its own scripts (Vite dev server, Cloudflare Pages). It does **not** weaken isolation: the escape hatch only applies when the iframe and parent share the same origin — they don't.

**Thread isolation (Web Worker)**

The iframe spawns a Web Worker for all user code execution. Workers get their own OS thread. An infinite loop (`while(true){}`) blocks only the worker thread — the main app and iframe event loop remain fully responsive.

```
simten.dev (main app)
└── sandbox.simten.dev (hidden iframe — origin boundary)
    └── worker.ts (Web Worker — thread boundary)
        └── new Function(userCode)  ← untrusted code runs here only
```

### Network restriction (CSP)

The sandbox server sends a `Content-Security-Policy` header that restricts all outbound network requests from within the iframe:

```
Content-Security-Policy: connect-src 'self' https://esm.sh;
```

Code running inside the sandbox worker cannot call `fetch`, `XMLHttpRequest`, or open WebSockets to arbitrary hosts. Only `self` (the sandbox origin itself) and `https://esm.sh` (the npm CDN used for package imports) are allowed. This prevents a compromised or malicious circuit from exfiltrating source code or making requests to attacker-controlled servers.

This header is set in both the dev server (`vite.config.ts`) and production (`public/_headers` for Cloudflare Pages).

### Timeout and recovery

The sandbox sets a 5-second timeout per request. If the worker doesn't respond:

1. `worker.terminate()` kills the hung thread
2. A fresh worker is spawned immediately
3. Any requests pending against the old worker are resolved with `'Worker restarted'` so the caller can retry

The main app never hangs. The sandbox recovers transparently.

### Why the simulator is split across two threads

The same engine runs in two places inside the sandbox: an ephemeral instance in the **worker** during `compile` and headless `simulate`, and a persistent instance on the **iframe main thread** that drives the live canvas (`tick`, `setNode`, `snapshot`, `restore`). The main thread never runs user code — only already-compiled IR — so it cannot hang.

Both threads share identical security guarantees (same origin, same CSP). The split is not about one being safer; it is about **runaway recovery**. `worker.terminate()` is the only way out of a `while(true){}` in user code. If the canvas sim shared that thread, every bad loop would wipe switch positions, cycle count, and snapshots. Keeping the persistent sim on the side that can't hang makes a runaway cost the user 5 seconds and an error toast, not their session.

This is structural crash isolation — it falls out of *where* code runs, not from careful error handling. The cost is one extra postMessage hop per tick, well under the frame budget.

### postMessage boundary

All communication between the main app and the sandbox crosses a `postMessage` boundary. Only plain JSON is sent in either direction. The `compile` response returns `Circuit[]` (plain IR objects with no executable code) — not `BuiltCircuit` instances, which carry function references. The main frame reconstructs a `BuiltCircuit` from the IR after the boundary is crossed.

### npm imports

Circuit code can use `import` statements to load npm packages:

```ts
import fc from 'fast-check';

const MyCircuit = circuit('MyCircuit', { ... });
```

When the worker detects import statements, it:

1. Extracts them and rewrites bare npm specifiers to `https://esm.sh/<package>`
2. Builds a loader ES module and dynamically imports it via a Blob URL
3. Merges the resolved package values into the scope passed to the circuit executor
4. Revokes the Blob URL immediately after loading

`@simten/*` imports are silently skipped — those names are already in scope and don't require a network fetch.

This all happens inside the sandbox worker. The main frame never touches the npm packages.

### What is and isn't blocked

| Attack | Status |
|--------|--------|
| Access `simten.dev` cookies / localStorage | Blocked — origin isolation |
| Access `simten.dev` DOM | Blocked — origin isolation |
| `window` object from user code | Blocked — runs in Worker (no `window`) |
| `localStorage` from user code | Blocked — `localStorage is not defined` in Worker |
| Infinite loop blocking the UI | Blocked — Worker on separate OS thread, 5s timeout |
| HTTP requests to arbitrary hosts | Blocked — `connect-src` CSP on sandbox server |
| Source code exfiltration via `fetch` | Blocked — `connect-src` CSP on sandbox server |
| `new Function()` in main frame | Blocked — enforced by automated invariant tests (see below) |

## MCP Sandbox

When Claude calls `simulate_circuit` or `check_circuit`, the circuit source runs in a forked child process — not in the MCP server process itself. The MCP process (which inherits your shell environment and runs with your full filesystem access) never executes user circuit code.

### Architecture

```
MCP server process (full env, full fs)
└── fork() → sandbox-child.cjs (isolated child)
    ├── env: {}              — no API keys, no HOME, no PATH
    ├── --permission         — Node.js permission model
    ├── --allow-fs-read=<bundle-path>   — only the bundle itself
    └── new Function(userCode)  ← untrusted code runs here only
```

### Empty environment

The child is forked with `env: {}`. `process.env` is completely empty:

- `process.env.HOME` → `undefined`
- `process.env.PATH` → `undefined`
- All other environment variables → `undefined`

Even if circuit code tries to read environment variables (API keys, secrets inherited from your shell), there is nothing there to steal.

### Node.js Permission Model (`--permission`)

The child is started with Node.js's built-in permission model. With no `--allow-fs-read` paths specified (except the bundle itself), all filesystem reads throw `ERR_ACCESS_DENIED`:

```
fs.readFileSync('/etc/passwd')        → ERR_ACCESS_DENIED
fs.readFileSync('~/.ssh/id_rsa')      → ERR_ACCESS_DENIED
fs.readFileSync('~/.aws/credentials') → ERR_ACCESS_DENIED
```

This is enforced at the Node.js runtime level — JavaScript overrides cannot bypass it.

With no `--allow-child-process`, subprocess spawning is also blocked:

```
child_process.exec('curl ...')   → ERR_ACCESS_DENIED
child_process.spawn('wget ...')  → ERR_ACCESS_DENIED
```

### Self-contained bundle

The `--permission` model requires explicitly listing every file the child is allowed to read. Since the child needs `@simten/core` and its dependencies, naively listing all module paths would be fragile (especially with pnpm symlinks).

Instead, `sandbox-child.ts` is bundled at build time with esbuild into a single self-contained `sandbox-child.cjs` file. All dependencies are inlined — no external module reads are needed at runtime. The only `--allow-fs-read` needed is the path to that one bundle file.

### Lifecycle

- Spawned lazily on the first tool call
- Reused across all subsequent calls in the same MCP session (~1–5ms IPC overhead)
- Killed and respawned on timeout (30s) or unexpected exit
- All requests pending against a dead child are resolved with an error immediately

### What is and isn't blocked

| Attack | Status |
|--------|--------|
| Read inherited env vars (API keys, secrets) | Blocked — `env: {}` |
| Read `~/.ssh/id_rsa` | Blocked — `--permission` |
| Read `~/.aws/credentials` | Blocked — `--permission` |
| Read any file outside the bundle | Blocked — `--permission` |
| `child_process.exec('curl ...')` | Blocked — `--permission`, no `--allow-child-process` |
| Infinite loop / hung simulation | Blocked — 30s timeout, kill + respawn |
| HTTP requests / crypto mining | Not kernel-restricted — but `env: {}` means no credentials to exfiltrate, and the 30s timeout limits mining windows |

## Automated invariant tests

To prevent accidental re-introduction of unsafe code execution patterns in the main frame, the test suite includes invariant checks that scan all source files in `apps/tanstack/src` and `packages/embed/src`:

- No `new Function(` calls — the underlying primitive behind all dynamic code execution
- No imports of `executeCircuitCode` or `executeJsCode` — the core functions that call `new Function()`

These tests run in CI and fail immediately if either pattern appears outside the sandbox worker.
